# Architecture & design notes

Companion to the [README](../README.md). This document covers *why* the project is wired
the way it is, and the non-obvious behaviour worth knowing before changing it.

## Request flow

```
GET /api/v1/software-engineers
        │
        ▼
SoftwareEngineerController          @RestController, constructor-injected service
        │  getAllSoftwareEngineers()
        ▼
SoftwareEngineerService            @Service, business-logic seam (currently a pass-through)
        │  findAll()
        ▼
SoftwareEngineerRepository          Spring Data JPA proxy (no implementation written)
        │
        ▼
Hibernate ──► HikariCP ──► PostgreSQL :5332
        │
        ▼
software_engineer  +  software_engineer_tech_stack
```

At startup, `DataSeeder` (a `CommandLineRunner`) runs once the context is ready and
inserts sample rows **only if the table is empty**.

## Data model

Two tables, both generated by Hibernate from `SoftwareEngineer`:

```
software_engineer                    software_engineer_tech_stack
├── id    uuid PK                    ├── software_engineer_id  FK → software_engineer.id
└── name  varchar                    └── tech                  varchar
```

`id` is a `UUID` with `@GeneratedValue(strategy = GenerationType.UUID)` — Hibernate
generates the value on persist, so it is `null` on a transient instance and set by the
time `save()` returns. It replaced an `IDENTITY` integer; nothing in the app depends on
ids being sequential or server-assigned by Postgres.

`techStack` is a `List<String>`, which has no single natural column type. It is mapped
with `@ElementCollection` + `@CollectionTable`, so each entry becomes a row in the side
table. The alternative — storing a delimited string in one column — is simpler but makes
querying individual technologies impossible.

`fetch = FetchType.EAGER` is set deliberately. `@ElementCollection` defaults to `LAZY`,
which happens to work today only because `spring.jpa.open-in-view` is enabled by default —
Spring holds the persistence context open through view rendering, so Jackson can still
trigger the collection load while serialising. That default is widely disabled (Boot logs
a warning about it at startup, since it hides queries in the rendering phase), and the
moment it is turned off a lazy `techStack` fails to serialise. Fetching eagerly keeps the
mapping correct on its own terms rather than depending on that setting.

## Design decisions

### Docker Compose support drives the database lifecycle

`spring-boot-docker-compose` is on the classpath, so during development Spring finds
`compose.yaml`, runs `docker compose up`, discovers the Postgres service, and derives the
datasource connection details from the running container — no configuration required.

Two consequences that trip people up:

1. **It is excluded from the executable jar.** `spring-boot-maven-plugin` strips both
   `spring-boot-docker-compose` and `devtools` when repackaging. `java -jar` therefore has
   no compose support and falls back to the explicit `spring.datasource.*` properties.
   That is exactly why those properties exist even though development doesn't need them.
2. **It is skipped in tests.** `spring.docker.compose.skip.in-tests` defaults to `true`,
   so `@SpringBootTest` will not start the database. Tests rely on the same explicit
   properties and require a running container.

`spring.docker.compose.lifecycle-management=start-only` overrides the default
`start-and-stop`, which would stop the Postgres container every time the app shuts down —
tedious during a normal edit-run-test cycle.

### The `app` service sits behind a compose profile

`compose.yaml` describes both the database and the application image. Without a profile,
Boot's compose support would start *both* on every IDE run — rebuilding the application
image to run an application that is already running locally.

`profiles: ["full"]` on the `app` service means:

- `docker compose up` / IDE runs → database only
- `docker compose --profile full up` → full stack

One file, no duplication, and no accidental image builds.

### Host port 5332, not 5432

`compose.yaml` publishes `5332:5432` so the container never collides with a Postgres
instance installed on the host. Anything connecting from the host uses **5332**; anything
connecting from inside the compose network (the `app` service) uses `db:5432` — the
published-port mapping applies only on the host, so inside the network Postgres is still
on its default 5432. That is why the `app` service carries its own `SPRING_DATASOURCE_URL`
pointing at `db:5432` rather than reusing the host-facing `5332`.

### Schema by `ddl-auto=update`

Hibernate reconciles the schema with the entity classes on startup — adding any missing
tables and columns — and leaves the data in place. Chosen so the persistent
`postgres_data` volume in `compose.yaml` actually means something: rows survive an
app restart, and the `DataSeeder` guard below has real work to do.

It replaced `create-drop`, which dropped the whole schema on every JVM shutdown (and
could drop tables mid-run under a devtools restart, leaving the app up with no tables) —
fast to iterate on, but it wiped the volume on every run and made the seeder guard inert.
`update` keeps the iteration speed for additive entity changes without the data loss.

The trade-off is `update`'s usual one: it only adds, never alters or drops, so a renamed
or removed field leaves a stale column behind, and there is no reviewable schema artifact.
Nothing you would point at a shared or production database. Migrating to Flyway later
means adding `spring-boot-starter-flyway`, capturing the current schema as `V1__init.sql`,
and setting `ddl-auto=validate`.

### Seeding is guarded, not idempotent by luck

`DataSeeder` checks `repository.count() > 0` and returns early. Under `ddl-auto=update`
the `postgres_data` volume carries rows across restarts, so on the second launch the
table is non-empty and the guard is what stops a duplicate set of engineers being
inserted every time. The guard is on row count rather than specific IDs, so an
intentionally emptied table re-seeds on the next run.

## Known rough edges

These are inherited from the project template or the course exercises and are not load-bearing:

- **`graphqlcodegen-maven-plugin`** is configured against `src/main/resources/graphql-client`,
  which does not exist. The build passes because the plugin finds no schemas. Dead config;
  safe to delete along with the `build-helper-maven-plugin` block that adds its output
  directory as a source root.
- **`spring-modulith-starter-core`** is a dependency but no modules are defined. It costs a
  little startup time and nothing else.
- **`SoftwareEngineer.equals`/`hashCode`** are IDE-generated over all fields including the
  generated `id`. For a JPA entity this is fragile — the hash changes once the entity is
  persisted and receives its `id` (still true with the UUID strategy: the value is assigned
  on persist, not at construction). It works here because entities are never put in
  hash-based collections before saving.

## The write path

`POST /api/v1/software-engineers` creates one engineer, through the same
`Controller → Service → repository` seam as the read path.

- **The request body is `CreateSoftwareEngineerRequest`, not the entity.** Binding
  `@RequestBody SoftwareEngineer` directly would let a caller supply `id`.
  `JpaRepository.save` picks insert vs. update from `isNew(entity)`, which for a
  `@GeneratedValue` UUID with no `@Version` is just `id == null` — so a body with a
  known `id` (and every `id` is returned by the GET) would `merge()` over an
  existing row, and a partial body would null out that row's `techStack`. The
  request record carries only `name` + `techStack`; the service maps it to a fresh
  entity with a `null` id, which forces the insert path.
- **Input is validated** (`@Valid` on the parameter, `spring-boot-starter-validation`
  on the classpath): `name` `@NotBlank @Size(max = 255)`, `techStack` `@NotEmpty`
  (`@Size(max = 50)`) of `@NotBlank @Size(max = 255)`. The `@Size` caps bound what
  one unauthenticated request can persist; 255 matches Hibernate's default
  `varchar` length. A violation is a 400 before the service is called.
- **Responds `201 Created`** with the persisted entity so the caller learns the
  generated `id`. No `Location` header — there is no GET-by-id endpoint to point it
  at yet. IDEA Ultimate's taint analysis (`JvmTaintAnalysis`) flags the entity in
  the response body as request-derived data reaching an XSS sink; it is suppressed
  at the `return` with a comment — the `@RestController` serialises JSON, which is
  not an HTML sink, and the fields are length-bounded above.

Still open, in rough order of value: a response DTO so the JPA entity isn't the API
contract on the way out either, `@RestControllerAdvice` for error handling (the 400
above is Spring's default shape), a GET-by-id endpoint (+ `Location` on create),
Flyway for schema management, and Testcontainers so tests provision their own
database instead of depending on a running container.
